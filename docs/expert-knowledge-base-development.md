# 跨境医疗私有知识库开发方案

版本：v0.2（方案及交互原型，2026-10-22）

目标：把专家审阅中确认有效的医学内容，沉淀为可追溯、可检索、可反哺方案生成的私有垂直知识库。

本次交付为开发方案和独立原型，不代表正式功能已经接入。当前线上专家审阅、报告生成、直接发布策略和数据库均不修改。流程确认后，再实施人工录入、管理员最终审核和候选池接口。

## 零、需求与现有系统衔接

### 业务目标

- 团队按病种人工盘点和填写治疗手段、药物、设备、就医资源等资料，逐病种积累，不要求 AI 自动盘点后直接入库；
- 团队各自找到的资料、专家审阅中确认的可复用内容、可信来源的定向定期抓取，进入同一套整理与审核流程；
- 账号权限控制录入和审核，由管理员最终确认，未审核内容不用于报告生成；
- 知识作为有版本的检索参考，不等同于给大模型训练“永久记忆”；
- 后续可从已发布知识派生网站科普/SEO 内容，但需另做内容审核和医疗宣传合规检查，不自动发布病例或医学结论。

### 存量能力与本次新增

现有 `src/expert/` 和 `src/routes/expertReview.ts` 已有审阅来源的知识、混合检索、条件核验和引用追溯。当前知识列表通过审阅/病例关联查询，不能直接承载没有病例关联的人工录入内容；已有批准接口处于关闭状态，不能把原型按钮视为已具备后端能力。

现行部署允许 `expert_published` 直接反馈；本方案正式接入后，**新录入及新提交知识必须经过管理员发布为 `approved`**。迁移前需盘点存量 `expert_published`，由管理员决定补审与切换时点，不能静默批量标记为管理员审核通过。确认前不切换线上配置，不阻断现有报告生成。

## 一、产品边界

知识库不是自动训练模型，也不是把单个患者的病例原文直接变成通用医学结论。系统只允许保存经过人工整理、带来源和适用边界的知识；新报告生成时，模型只能读取“已发布”且满足病例条件的知识版本。

本阶段包含：

- 人工选择病种并录入知识；
- 专家提交、管理员最终审核；
- 网络抓取候选池（只做候选，不自动入库）；
- 版本、来源、审核和撤回追溯；
- 按病种、模块、关键词、适用条件为方案生成提供检索参考；
- 生成时记录实际引用的知识 ID、版本和匹配理由。

本阶段不包含：自动模型训练、自动发布、患者病例自动入库、绕过权限的原文抓取、未经审核的医疗建议直接展示。

## 二、角色与权限

| 角色 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 专家 | 查看全部病例；创建/编辑知识草稿；提交审核；查看自己提交的审核结果 | 发布、退回他人条目、删除正式版本 |
| 内容编辑（可按人员情况开通） | 人工选择病种、整理来源、保存草稿、提交审核、处理候选资料 | 不得擅自形成医学结论、发布知识或获取患者原始身份资料 |
| 管理员 | 查看全部条目；审核、退回、发布、下架、撤回；配置抓取规则；查看审计记录 | 不得修改原始病例和正式报告 |
| 资料处理人员 | 处理附件脱敏和资料质量状态 | 不得修改医学知识结论、不得发布知识 |
| 系统 | 执行字段校验、版本锁、检索、引用追溯 | 不得自行判断医学结论并发布 |

管理员最终审核是本方案的硬门禁：只有管理员点击“通过并发布”后，条目状态才变为 `approved`，才可进入后续方案生成。专家提交后的状态为 `pending_confirmation`。

## 三、知识录入流程

```text
专家选择病种/模块
        ↓
填写知识条目与来源
        ↓
保存草稿（可继续编辑）
        ↓
提交审核（版本锁定）
        ↓
管理员审核：通过发布 / 退回修改 / 驳回
        ↓
建立检索索引
        ↓
新报告按病种、模块、条件匹配并记录引用
```

拟开发状态（不是现有数据库全部已支持的状态）：

| 状态 | 含义 | 是否参与生成 |
| --- | --- | --- |
| `draft` | 专家草稿 | 否 |
| `pending_confirmation` | 专家已提交，等待管理员 | 否 |
| `approved` | 管理员确认发布 | 是 |
| `returned` | 管理员退回修改，必须填写原因 | 否 |
| `rejected` | 管理员正式驳回，不再继续此版本 | 否 |
| `withdrawn` | 已撤回/失效 | 否 |
| `expired` | 超过复核期限 | 否 |

`draft → pending_confirmation → approved / returned / rejected`；退回后从原提交快照建立修订，重新提交；发布后禁止覆盖原版本，只能新建修订草稿。新版本批准时，以事务切换当前有效版本，旧版保留完整内容与引用关系。复核到期可由查询计算为过期，但必须在检索时按时间拦截，不能只依赖定时任务更新状态。

## 四、知识条目字段

### 4.1 病种与分类

- 病种：从标准病种库搜索选择；支持新增病种申请，不直接修改标准字典；
- 别名/英文名；
- ICD 编码（可选，但有则优先）；
- 专科；
- 内容类型：治疗方案、药物、手术方式、医疗设备、康复与随访、风险与禁忌、跨境就医注意事项、费用/资源规则；
- 关联报告模块：病历解读、病情评估、治疗路径、费用预算、医院选择、随访等。

### 4.2 医学内容

- 标题；
- 核心结论（必须能独立理解）；
- 详细说明；
- 适用人群/适应症；
- 不适用条件/禁忌症；
- 风险与不确定性；
- 可选替代方案；
- 适用前提（例如分期、指标阳性、术前/术后）；
- 需要医生再次确认的事项。

### 4.3 跨境服务信息

- 适用国家/地区；
- 可提供该技术的机构类型（不把未核实的机构写成确定推荐）；
- 语言、签证、陪诊或随访注意事项；
- 费用和可及性说明（只记录来源明确的范围，不承诺固定价格）。

治疗、药物、设备另建议增加：通用名/商品名/技术名、监管批准机构及适应症、已批准/指南涉及/仅临床研究/待核实、批准国家或地区、登记编号和查询日期。临床试验不等于常规治疗，医院宣传不等于有效性证据。“国内有、国外没有”必须限定地区和日期，不能写成无边界的营销结论。

### 4.4 证据来源

- 来源机构；
- 原文链接、DOI 或官方文档编号；
- 来源发布日期；
- 证据类型：官方监管/临床指南/系统综述/同行评审研究/机构资料/待核实；另外保留专家对证据质量、推荐强度和局限性的评价，不按网站名或来源类型自动判断疗效等级；
- 引用摘要；
- 证据附件；
- 抓取时间（自动来源）；
- 来源内容哈希（用于发现变更）。

### 4.5 AI 检索与生命周期

- 检索关键词、疾病同义词、治疗同义词；
- 必须同时出现的条件词；
- 排除条件词；
- 适用地区标签；
- 生效日期、下次复核日期；
- 创建人、审核人、版本号、变更说明；
- 状态和撤回原因。

## 五、入库标准与校验

提交前强制校验：

1. 病种、内容类型、目标报告模块、标题、核心结论、适用条件、不适用条件、风险、来源、引用摘要、证据类型和下次复核日期不能为空；
2. “修改/补充”必须填写医学依据，不能只有个人判断；
3. 适用条件和排除条件不得互相矛盾；
4. 结论必须与来源一致，不得使用“百分之百”“绝对安全”等未经证实的表述；
5. 不得写入姓名、电话、邮箱、证件号、病历号、文件名等患者身份信息；
6. 单个病例事实必须改写为可泛化的医学规则，并保留原病例来源位置供审计；
7. 费用、疗效、资源可及性必须标注时间和不确定性；
8. 来源冲突时进入“待处理”，不得自动取平均或自动选一条发布；
9. 有效期到期后自动停止检索，重新复核后生成新版本；
10. 任何发布、退回、下架、撤回操作与内容变更摘要写入追加式审计日志；业务接口禁止改写日志，配合数据库权限与独立备份防篡改，不宣称仅凭一张日志表即可绝对不可篡改；
11. 可接受原文 URL、DOI 或受控归档编号；没有公开链接不等于没有证据，但必须能由审核人访问和核验原件；
12. “待核实”证据允许暂存/提交但禁止发布。相关技术涉及监管适应症时，未核实的批准状态也必须拦截发布；
13. 自动检查疑似个人信息和不当承诺只能辅助，不能保证识别所有隐私和医学错误，最终仍由人工核验；
14. 管理员发布必须提交审核清单和意见；修改已发布内容不得绕过重新审核。

管理员审核清单：原文是否支持结论、是否适合泛化、适用/排除与风险是否完整、隐私是否已清除、无夸大承诺、模块及地区是否合适、复核期限是否合理。管理员是平台最终发布角色，不等于具有医学资格；非医学管理员遇到医学判断，必须先取得专家确认记录再发布。

## 六、网络抓取候选池

### 6.1 建议范围

优先来源：WHO、各国卫生/药监机构、医学专业协会、临床指南发布机构、公开论文和系统综述、正规医院/大学医学中心、药品和设备官方资料。

不直接作为正式来源：个人博客、论坛、自媒体、短视频、无法核实作者的商业文章、夸大疗效的营销页面。

### 6.2 频率

| 来源类型 | 建议频率 | 处理方式 |
| --- | --- | --- |
| 监管公告、药品安全、重大指南 | 每日发现变更 | 进入高优先级候选 |
| 临床指南、专业机构 | 每周扫描 | 进入候选池并去重 |
| 医学论文/系统综述 | 每周收集、每月整理 | 专家筛选后才可入库 |
| 医院/服务资源 | 每月或每季度复核 | 重点检查是否仍可提供 |

### 6.3 合规边界

- 遵守 robots.txt、网站条款、版权和访问频率限制；
- 不绕过登录、付费墙或访问权限；
- 不抓取患者个人信息；
- 不完整复制受版权保护文章，只保存标题、摘要、链接、来源哈希和必要引用；
- 抓取结果只进入 `crawl_candidate` 候选状态，不能直接参与生成；
- 每条候选保留 URL、抓取时间、来源、哈希、解析状态和人工处理记录；
- 抓取失败、来源失效或内容变更时，提示管理员复核，不自动覆盖已发布版本。

### 6.4 初始运行建议

先限定 2–3 个重点病种、10–20 个来源白名单试运行，作为容量建议而非已承诺覆盖率；管理员手工配置病种、关键词、地区、来源和频率。优先订阅官方 RSS、公开 API 或更新页，逐站确认条款后才启用抓取。

每域并发初始为 1、请求间隔至少 5 秒、单任务增量获取不超过 50 页；服务端更严格限制优先，遇到 429/403 停止或按 Retry-After 退避，不以代理、换 IP 绕过限制。使用 URL 规范化、正文哈希和相似度提示去重；同来源更新建立候选修订，不直接覆盖已发布版本。

抓取由服务端白名单任务执行，禁止对用户任意 URL 直接请求：校验域名、协议、每次重定向及 DNS 解析结果，阻止 localhost、内网、云元数据地址和 SSRF；设置大小、MIME、解析时间与下载限制。引用内容作为不可信数据，清洗脚本和提示注入语句，不能作为系统指令或触发工具调用。

## 七、AI 匹配与方案生成

1. 从脱敏病历、报告模块和高置信医学事实生成检索上下文，不使用身份信息；
2. 先按病种、发布状态、有效期、模块和硬性排除条件过滤；
3. 再使用关键词/BM25 + 多语言向量进行混合排序；
4. 对候选条目进行适用性核验，要求能在当前病例中找到连续原文证据，处理否定、疑似、分期及指标阳阴性；
5. 冲突、缺失证据、低相关、已过期或核验失败的条目不进入模型上下文；
6. 每个报告模块最多引用 3 条，整份报告按上下文预算限制；
7. 记录知识 ID、版本、匹配分、匹配理由、适用性证据和实际提供给模型的模块；
8. 匹配分不是临床概率，引用知识也不代表模型已经采纳；
9. 历史报告不回写、不重生成，知识只影响之后的新报告。

撤回/到期在读取上下文前再次校验。已经开始生成的任务保存知识快照及当时的发布依据；后续撤回不偷偷改写历史引用，但要能追溯并提示复核。第一版延续当前检索基础，先把新数据来源接入，不能在原型阶段把字面关键词演示描述成已完成的医学智能算法。

## 八、建议 API 与数据表

### API

- `GET /api/expert/knowledge`：扩展现有列表，按状态、病种、模块、来源类型分页查询；
- `POST /api/expert/knowledge/drafts`：创建人工草稿；
- `PUT /api/expert/knowledge/:id`：编辑草稿或退回后版本；
- `POST /api/expert/knowledge/:id/submit`：提交管理员审核；
- `POST /api/expert/knowledge/:id/approve`：管理员通过并发布；
- `POST /api/expert/knowledge/:id/return`：管理员退回，原因必填；
- `POST /api/expert/knowledge/:id/reject`：管理员驳回，原因必填；
- `POST /api/expert/knowledge/:id/withdraw`：管理员撤回；
- `GET /api/expert/knowledge/:id/versions`：查看版本和变更；
- `GET /api/expert/knowledge/candidates`：抓取候选池；
- `POST /api/expert/knowledge/candidates/:id/import`：导入为草稿；
- `GET /api/expert/knowledge/matching-preview`：用脱敏病例预览匹配结果，不写入报告。

### 数据表建议

在现有 `expert_knowledge` 基础上增加：

- `source_type`、`source_url`、`source_hash`、`source_published_at`；
- `evidence_type`、`evidence_quality`、`evidence_excerpt`、`evidence_files`；
- `content_type`、`specialty`、`region_tags`；
- `risks`、`alternatives`、`review_due_at`、`change_note`；
- `created_by`、`submitted_at`、`rejected_by`、`rejection_reason`；
- 独立 `knowledge_versions`、`knowledge_crawl_candidates`、`knowledge_audit` 表。

数据关系建议：

```text
知识条目 knowledge_entries（逻辑 ID / 当前发布版本）
    └─ knowledge_versions（不可覆盖的提交与发布快照）
         ├─ knowledge_sources（URL / DOI / 归档及引用位置）
         ├─ knowledge_audit（操作人 / 版本 / 动作 / 意见）
         └─ 报告引用（知识 ID + 版本 + 当时内容摘要）
候选 knowledge_crawl_candidates ──导入──> 人工草稿
专家审阅来源 ──提炼──> 人工草稿（保留受保护的来源关联）
```

必须解耦“知识必须来自病例”的现有关联和内连接列表，支持 `manual / review / crawl` 三类来源，不使用虚构病例或虚构审阅记录占位。保留现有审阅知识 ID 与历史报告引用，向量缓存键包含新知识版本、正文哈希及模型版本。源附件只保留受控文件引用，不把患者原件放进公用知识文档。

所有发布和审核接口必须在服务端校验角色、条目所有权、版本号、状态流转和 CSRF；前端隐藏按钮不能替代后端权限。沿用账号系统，不提供自助成为管理员；对现有 `knowledge_confirmer` 与管理员角色进行明确映射。草稿更新使用乐观锁，批准/退回/撤回使用事务与幂等键；版本过期返回 409，无权返回 403。列表不能因来源无病例关联而漏项。

## 九、原型范围

原型文件：`Studio-huanyu-Client/prototypes/knowledge-base/index.html`。

原型包含：

- 角色切换（专家/管理员）；
- 知识库概览、人工录入表单、字段校验；
- 全部条目、草稿、退回、待审核、已发布、撤回及抓取候选视图；
- 管理员通过发布/退回；
- 抓取候选导入人工草稿；
- 发布版修订、撤回与演示会话操作记录；
- 按当前演示数据变化的引用预览和引用追溯（字面规则，不是真实 AI 匹配）；
- 所有操作为浏览器内存演示，不写正式数据库，不改变当前线上“专家直接发布”配置。

## 十、实施顺序

1. 先上线人工草稿、字段校验、管理员审核和版本审计；
2. 接入抓取候选池，先支持人工导入，不自动发布；
3. 将现有专家审阅知识写入统一版本模型；
4. 把报告生成检索改为只读取 `approved` 版本；

## 十一、正式开发验收标准

1. 内容编辑/专家能手工选择病种、填写类型与内容，保存、继续编辑、提交；缺失必填项能准确定位。
2. 越权调用服务端发布/退回/撤回接口被拒绝；停用账号会话失效；管理员操作和理由可追溯。
3. 待审核、退回、驳回、撤回、过期或未核实内容无法进入新报告提示词；管理员审核清单不可仅在前端校验。
4. 并发编辑产生明确 409；重复提交/重复审批不重复建版本；来源、附件和草稿不会因失败而丢失。
5. 修订期间旧发布版正常使用；新版本通过后原子切换；历史报告仍能追到原知识版本。
6. 人工条目不依赖虚构病例关联，审阅来源能追到脱敏资料位置；抓取候选可去重、导入、忽略并恢复。
7. 条件否定、分期、受体状态、地区批准范围等高风险冲突必须拒绝或交专家确认；召回或核验失败不拿低质内容兜底。
8. 抓取任务通过 robots/版权边界、限流、SSRF、恶意页面与大文件测试；无登录/付费墙绕过。
9. 完成录入→提交→退回重提→批准→引用→修订→撤回的端到端测试，保留版本及引用证据。
10. 先在隔离测试数据上验证，再备份、迁移、灰度切换发布策略；回滚只回程序与配置，不删除病例、知识、审核及历史引用。
